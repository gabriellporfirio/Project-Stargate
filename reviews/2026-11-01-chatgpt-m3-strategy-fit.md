# ChatGPT review: M3 strategy and fit engines

Reviewed PR #28 at `4a7184e8e507fed3418d10d6f8ef618a6ab2c5fe` on 1 November 2026. **Verdict: request changes.** The deterministic decision engine, separate model notes and parallel milestone planning are sound.

The boot-state mapping is supported by [AOSP](https://source.android.com/docs/security/features/verifiedboot/boot-flow). Retain its inference provenance; unknown/conflicting inputs must remain unresolved.

1. **Must fix — distinguish candidate strategies from proven eligibility (§3).** Treble plus an unlock path is insufficient: [Android's GSI checks](https://developer.android.com/topic/generic-system-image) also consider launch/version compatibility and matching architecture. M2's wiki listing proves page existence, not a working Linux port; absence from LineageOS's current list doesn't prove a community build impossible. Keep unsupported conclusions unknown or label a deliberately narrower policy. The app fallback also needs app/runtime requirements before promising compatibility. Define an exclusive unlock truth table: `locked=false, supported=false` currently satisfies both “possible” and “impossible”; `locked=true, supported=true, allowed=false` is currently blocked from unlocking, not merely missing information. Separate [present permission](https://source.android.com/docs/core/architecture/bootloader/locking_unlocking) from permanent impossibility. Preserve contradictory lock evidence rather than overwriting it.

2. **Must fix — preserve uncertainty when selecting models (§4).** “No catalog model fits → refused” contradicts “unknown → unconfirmed.” With unknown model bytes, no candidate is proven to fit, but none is proven impossible. Evaluate candidates separately: select among confirmed budget fits; if none fit and some remain unknown, report unconfirmed with no confirmed choice; refuse only when all evaluated candidates definitely fail. An empty/incomplete catalog is not proof that no model can run. Budget RAM and storage for both selected services plus runtime/app overhead. Define what “largest” measures and a stable tie-break; label estimated fit. Separate model-resource checks from the always-unknown image-capacity check.

3. **Must fix — bind inputs and define M4's handoff (§1/6).** Validate input schemas and match research subject/codename to the profile before using facts; test a valid report for the wrong phone. Preserve synthetic/replay provenance. Require explicit selected services, chosen model artifact/file(s), revision, format/runtime, total bytes, budget/rule version and unresolved checks in `plan-v1`. Hashing a candidate catalog alone doesn't identify which model M4 must package. Unconfirmed may allow planning or an explicitly labelled emulator experiment; it must not establish device/build compatibility or permit deployment.

4. **Must fix — settle exit-code precedence (§6).** A refused selection plus a failed `--explain` currently qualifies for both 7 and 2/5. Keep refusal at 7, record explanation failure separately, and test the combination. Invalid inputs must fail before any model call.

5. **Should fix — make source verification executable (§2 and network limits).** Permit bounded development-time reads of the official sources needed for inference/catalog citations; keep ordinary planning offline and the two live validation runs bounded. Currently “nothing else” forbids those reads.

**Top three:** truthful strategy eligibility; model selection that preserves unknowns; an exact M4 contract tied to the correct device. No product code or live calls were tested. Existing no-phone/no-install rules remain sufficient for this milestone.
